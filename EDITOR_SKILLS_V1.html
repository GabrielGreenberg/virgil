1. What v1 is

v1 ships the Virgil editor plus a Claude session that knows Virgil thoroughly and can mechanically manipulate its structures: cards, paragraphs, atoms, tasks, the bibliography, the preamble. The skill set is small and focused — about fifteen skills, all of them mechanical. They route, dispatch, edit cards, manage tasks, manage the bibliography, swap styles. They don't draft footnotes, write quotations, search for citations, restructure paragraphs, or compress prose. All generative work happens in chat with Claude on demand, using v1's mechanical primitives as building blocks.

The design principle. Build the mechanics solidly first. Once Claude understands Virgil completely and can manipulate cards/atoms/paragraphs reliably, every smart operation a user could want — drafting a footnote, finding a citation, tightening a paragraph — can be composed on the fly in chat. No need to pre-design every smart skill; the mechanical layer is the substrate that supports all of them.

2. Virgil's ontology

Virgil's world is made of the Document and five primitives within it.

The Document

The Document is the container. It is composed entirely of TextObjects. Cards, Atoms, and the other primitives exist within the Document but are not themselves the Document. The Document is the world.

The five primitives

PrimitiveWhat it isMobility
TextObjects The structural atoms of text — paragraphs, headings, examples, quotation groups, blockquotes. Each is discrete and addressable. Move, pop, drop freely.
Atoms Inline elements within TextObjects, finer-grained than TextObjects but not themselves TextObjects. Examples: in-text citations (\cite{}), footnote markers (\footnote{}), refs (\ref{}), inline math ($...$). Atoms are often bidirectionally linked to Cards. Text-bound — move with the surrounding text when cut/copied/dragged. Don't pop into Panels independently.
Cards Almost everything else: notes, todos, footnotes, citations, quotations, bibliography entries, suggestions, comments, annotations, Tasks. Cards are not a sub-type of TextObject — they're a parallel structure that connects to text via anchors and/or Atom links. Move, pop, drop freely.
Omni-View gutters The in-line rendering of Cards alongside the text they're anchored to. The primary surface for seeing Cards in context. —
Panels Sidebar collections that list Cards of a given kind (Notes panel, Footnotes panel, Bibliography panel, Inbox panel for Tasks). The secondary surface — used for browsing, filtering, and bulk operations. —

Linkage: how Cards connect to text

Cards connect to text in two distinct ways — both are properties of the Card, not separate primitives:

  • Anchor — a Card's positional pointer to a TextObject. One-way: the Card knows its anchor; the TextObject doesn't directly know what's anchored to it. Coarse-grained (paragraph-level). Notes and todos typically have only an anchor.
  • Atom link — a Card's bidirectional relationship with an inline Atom. The Card and the Atom both know about each other. Fine-grained. Footnote Cards have an Atom link to their \footnote{} marker; citation Cards have Atom links to every \cite{} instance.

Some Cards have only an anchor (notes). Some have only Atom links (a bibliography Card with many \cite{} Atom links and no paragraph anchor of its own). Some have both (a footnote Card is anchored to a paragraph AND atom-linked to a \footnote{} marker within that paragraph).

UUIDs — the identity layer

Every TextObject, Atom, and Card carries a UUID. The user never sees a UUID directly; Virgil uses them for stable reference across edits, linkage resolution, and the move/pop/drop affordance.

  • %!v: at line-end of a paragraph in .tex marks a TextObject UUID.
  • \vcid{} marks a citation Atom UUID.
  • \vfid{} marks a footnote Atom UUID.
  • \vexid{} marks an example reference Atom UUID.
  • Cards carry their UUIDs in their sidecar JSON entries ("id": "...").

Tasks as a Card kind

A Task is a Card with lifecycle states (see §7). The Inbox is the Panel that surfaces them. ai-requests.json is their sidecar. Tasks can have anchors, Atom links, both, or neither (a Task: "review the whole doc" has no anchor).

4. Voice & persona

Claude speaks as Virgil for first-order users. First-person where natural ("I added a footnote here"); notes left in sidecars carry author: "virgil"; user-facing copy never names "Claude" or "the model."

For meta / dev work (running from the repo, iterating on the skill set, debugging the cowork plumbing), the persona shifts: Claude is Claude doing engineering work. The boundary is detectable at runtime — a meta-skill never runs in a paper or library workspace.

The standard user

A writer — academic, essayist, researcher. They care about sections, paragraphs, sentences, citations, footnotes, quotations, the shape of the argument, register, tone, sources. They do not care about TipTap extensions, paragraph UUIDs, the %!v: marker convention, sidecar JSON schemas, apply_response.py's writeback transaction, what dispatch order the umbrella uses, version-bump etiquette.

Detail calibration

Detailed

  • The text itself: what changed, why a footnote works, what the new citation says.
  • Substantive editorial reasoning: argument structure, tone, register, claim/warrant relationships.
  • Sources: who said what, where, when — when verifiable.
  • Judgment calls: "I left this hedge because it's load-bearing for your argument."

Gestural (or silent)

  • Plumbing: "I wrote to footnotes.json and bumped version.txt" → "footnote added."
  • Schema vocabulary: "I created a RevisionSuggestionCard" → "I drafted a revision."
  • File paths, UUIDs, helper script names, JSON keys.
  • Internal dispatch: "I called sub-skill X via apply_response.py" → just do the work.

Core principles (mechanics-focused subset)

  1. Read before editing. Look at the surrounding paragraph, the adjacent cards, the bib state. Work that skips this rarely fits.
  2. Locate before acting. If the anchor is ambiguous, ask — don't guess. (See §5 on anchor resolution.)
  3. Trust the user's framing. "This is a manuscript citation, leave it alone" means leave it alone.
  4. Never fabricate. Sources, quotations, page numbers, DOIs — verifiable or absent.
  5. Garden as you go. Notice stale anchors, orphan footnotes, mismatched bibkeys while doing other work; mention them, offer to clean up.
  6. Stay in your lane. A skill doing card creation doesn't simultaneously refactor the bibliography. One ask, one action.
  7. Atomic by default. Each change lands fully or not at all. No half-written sidecars, no dangling references.
  8. Leave a trail. Every change leaves a trail. Default is explicit (the Inbox entry + the change itself); the user's chosen safety level controls visibility (§8).
  9. Surface uncertainty. Better to flag ambiguity than to ship a confident-sounding wrong answer.

5. The two workflows

Virgil supports two ways for a user to bring work to Claude.

Workflow A: UI-initiated (note-card-based)

The user creates a note card and AI-flags it. The existing card-flag bridge (bridgeCardAiRequestFlag()) converts the flagged note into a Task in ai-requests.json. Claude drains via /editor/review. There is no separate "Virgil form" widget — the note IS the input.

Two note variants, differing only by anchor type:

  • General note card — anchored to a paragraph (TextObject). For "Virgil, do this thing somewhere around this paragraph."
  • Selection note card — anchored to a text span within a paragraph (possibly to specific Atoms). For "Virgil, act on this specific text."

Both flow through the same data path. Skills receive a <requestId> and don't need to know which variant was the source.

The existing card-flag bridge also covers todos / cutter-comments / revision-comments for responder Tasks (a different semantic class — respond to this card rather than do this thing — same data path).

Workflow B: Claude chat

The user addresses Virgil directly in a conversational session. Virgil reads the conversation, resolves any ambiguity by asking, and acts.

Anchor resolution — the load-bearing rule for Workflow B

The burden is on whoever has the most context.

Workflow A queries arrive with maximal context. The UI captured the paragraph UUID, selected text, and surrounding state at the moment the user filed the request. Skills consume that and proceed.

Workflow B queries place the burden on the user to supply disambiguating context — quoted text, section name, paragraph reference, "the part where I talk about X." If Virgil can't resolve the anchor unambiguously from the chat, Virgil asks rather than guesses. There is no fallback precedence chain that lets Virgil silently lock onto its best-guess paragraph.

The proposed find_anchor.py helper (§13) is a resolver, not a guesser. It either finds an unambiguous match or returns a list of candidates for Virgil to surface back to the user. No skill ever proceeds with an anchor it isn't confident in.

6. Tasks vs Skills

Task is the user-facing unit of work. Skill is an internal unit. One Task may invoke many Skills; the user doesn't see or care which.

When a user files "add a footnote here about Smith", that's one Task. Behind the scenes, the umbrella might invoke create-card --kind=footnote, helper scripts to resolve the anchor, the apply_response.py writeback — but those are Skills, internal. The user sees one Task in the Inbox; one outcome.

Tasks are Cards (per the ontology in §2), with lifecycle states that other Card kinds don't share. They live in ai-requests.json and surface in the Inbox Panel.

Reporting is per-Task, not per-Skill

LevelWhat gets writtenWhere it goes
Per-Skill Terse dev one-liner: Done: footnote/<id>. Output: footnotes.json, document.tex. stdout — for the umbrella, logs, dev-dream memos. Never user-visible.
Per-Task User-facing Task summary (Virgil voice). e.g. "Added a footnote tracing Smith's claim back to Habermas." Written onto the Task Card as the resolution.
Inbox transition (status flip). The Task Card flips submitted → complete. The Inbox view IS the notification surface.
Chat reply (if Task was chat-initiated). Virgil's reply in the next conversational turn. Short or substantive depending on context.
Dev-dream memo (DEV mode only). editor/dev/memos/<date>/<skill>-<task-id>.md — captures the Task outcome for §14 learning.

The mechanism: the umbrella (or the chat-initiated entry skill) aggregates per-Skill dev one-liners into Task completion. apply_response.py has a Task-completion mode that writes the four surfaces atomically (§12).

8. Safety levels

Every Task carries a safety level describing how aggressively the user wants Virgil's work landed. The policy is per-Task, not per-skill — the user thinks in Tasks, so the policy lives there.

The three levels

LevelBehaviorWhat the user seesMaps to apply_response.py
Level 1 — Silently insert/change Skill performs the change directly. No surfaced card, no comment. The change is just there. Audit trail in the Inbox (Task with result: silent-applied) for retroactive checking. write-silent
Level 2 — Change, and leave a comment Skill performs the change directly. Leaves a sibling comment describing what was done. The change is live; an adjacent comment marks what happened. (result: auto-applied.) write-with-comment
Level 3 — Propose a change Skill drafts the change as a suggestion. Document is unchanged; user reviews and accepts or rejects. A suggestion card to act on. (result: accepted | rejected.) complete-task (with suggestion-card payload)

How the level is set

Per-Task field in ai-requests.json: safety_level: 1 | 2 | 3. Skills read it and dispatch to the matching apply_response.py subcommand.

  • Workflow A: the user picks the level explicitly when creating the AI-flagged note. The note's safety-level field becomes the Task's safety-level field at bridge time.
  • Workflow B: Claude asks the user for the level when not specified. If the user has standardized within the conversation ("from now on use level 2"), Claude carries that across subsequent Tasks in the conversation until told otherwise. No implicit default; no assumption.

The catastrophic-operation exception

Always warn before potentially catastrophic actions, regardless of the Task's safety level. If the work crosses a "catastrophic" threshold, the skill surfaces a one-time confirmation even when the Task says Level 1.

Catastrophic operations in v1:

  • style-merge — rewrites the preamble; affects rendering throughout the document.
  • sync-bib-to-library — renames citekeys throughout the doc; rewrites the bibliography.

The confirmation: "You asked for [Level 1]; this operation is a preamble rewrite that affects rendering throughout the document. Confirm silent, or downgrade to Level 2 / 3?" One confirmation per Task; if the user confirms, Virgil proceeds at the requested level for that Task.

9. The editing lock

When Claude is about to write files, it briefly takes the editing pen so the user can't be typing simultaneously and lose work. This is fully scripted inside apply_response.py's subcommands — no LLM in the loop, no token cost.

The mechanism

apply_response.py <subcommand> ...
  │
  ├─ acquire pen (one file write):
  │    write .virgil/pen-context.json:
  │      { "holder": "claude",
  │        "acquired_at": <ts>,
  │        "expires_at": <ts + 30s>,
  │        "prior_collab_enabled": <was-it-on?> }
  │    if collab was off, flip virgil/collab.json to enabled
  │    (pen.holder set to "claude" in same write)
  │
  ├─ do the atomic write (the subcommand's actual work)
  │
  └─ release pen (one file write):
       restore virgil/collab.json to prior state (off if it was off)
       delete .virgil/pen-context.json

Properties

  • Zero token cost. Dance happens inside Python, no LLM. Skills call apply_response.py <subcommand> ... as they would anyway.
  • Lock window: sub-second to a few seconds. Only the commit phase holds the pen — not the thinking phase. The user might wait 30 seconds for Claude to think; the actual lock window is the brief moment when files are being written.
  • TTL-based crash recovery. The expires_at field gives Virgil's poller an auto-release path. No background heartbeat process needed.
  • Transparent over collab state. If the user wasn't in collab mode, Virgil turns it on, does the write, and turns it off again. Prior state captured in pen-context.json at acquire time.
  • UI surface. When Claude has the pen, the Virgil UI shows the existing collab-locked rendering with adjusted copy: "Virgil is editing — please wait." A "Force release" button sits behind a confirmation for the case where Claude died and TTL hasn't fired yet.
  • Doc-level granularity. Lock the whole document, not individual paragraphs.

11. What's not in v1

Deferred to a future version. These are designed on the fly with chat-Claude using v1's mechanical primitives, OR deferred to v2 entirely (the user-dream layer).

Generative skills (designed ad-hoc in chat using v1 mechanics)

  • draft-footnote / find-citation / draft-quotation / draft-suggestion — content-generation skills. Replaced by chat-Claude composing the content + calling create-card mechanically.
  • The revision family — revise-compress, revise-cut-hedges, revise-flow, revise-make-explicit, etc. (~25 skills sketched). Chat-Claude does revision work directly on selected text.
  • The research family — research-paragraph, find-source, extract-quote, summarize-source, check-citation-fit, related-from-library, triangulate. Chat-Claude does research work using library_query.py-style direct access when needed.
  • The file-prep family — preflight, prep-file, convert-examples, expand-macros, migrate-preamble, migrate-bib, quarantine-tikz. File ingestion is a chat workflow in v1.

User-dream layer (deferred to v2)

  • The user-dream skill itself (per-user voice/preference learning).
  • ~/.virgil-user/ overlay storage (voice profile, commandment overrides, skill preferences).
  • <docpath>/.virgil/user-overrides/ per-doc layer.
  • Runtime layering (app < user-global < per-doc).
  • The revise-with-feedback meta-skill.
  • Aggregate signal upward (opt-in telemetry).

v1 preserves architectural optionality for the user-dream layer — see §15.

12. apply_response.py contract

The single sanctioned writeback path. Owns the atomic card-write + status-flip + notification + version-bump + pen-acquire/release transaction. Skills do not write files directly; they call apply_response.py with a payload describing what should land.

Subcommand architecture

SubcommandUsed byWrites atomically
complete-task Level 3 Tasks (propose a change), and direct-create skills like create-card for atom-bearing kinds (the artifact itself is the deliverable; user opted in by asking) Card (suggestion or direct-create artifact); Task with status: complete and result: review-pending | direct-created; user-facing summary on Task card; chat reply (if chat-initiated); inbox notification; version bump
write-with-comment Level 2 Tasks (change + comment) The change to .tex / sidecar; sibling comment card explaining the change; Task with result: auto-applied; inbox notification; version bump
write-silent Level 1 Tasks (silent insert/change) The change to .tex / sidecar; Task with result: silent-applied; inbox notification; version bump (no surfaced comment card)
complete-only Bib reviews and failure cases (no card produced) Status flip only, no card
revert Undo Remove card, reopen Task

Composable flag

  • --synthesize-task — creates the Task entry on the fly (for Workflow B / chat-initiated calls where the Task didn't pre-exist). Composable across all subcommands. Without this flag, the subcommand expects an existing requestId.

The atomic-write primitive

Every subcommand uses the same internal "write these N files atomically with rollback on failure" function. The pen-acquire/release from §9 wraps the atomic write. Atomicity guarantee: either all the files land or none of them do — the system never ends up in a half-state.

14. DEV mode + dev-dream

v1 ships a self-improving loop for the developer (not the end user). Every skill invocation under DEV mode is followed by a reflection memo. Overnight, the dream phase reads accumulated memos and refines the skill set.

DEV mode

A per-session toggle — probably VIRGIL_DEV=1 env var or a flag in document-settings.json. When on, every skill invocation gets a follow-up reflection pass that writes a memo at editor/dev/memos/<YYYY-MM-DD>/<HH-MM-SS>-<skill-name>.md. Never enabled in end-user sessions.

What the memo captures

BucketExamples
Issues / ambiguities / errors What was unclear in the skill prompt. Where Virgil had to ask the user for help. Where the user corrected Virgil mid-task. Where Virgil chose option A over B and isn't confident it was right.
Streamlining / repetition Multi-step inline operations that should be a helper. Skills that re-discovered the same fact inline. Awkward call sequences. Cross-skill duplication.
Alignment / fit Friction points where Virgil's default didn't match what the user actually wanted. Cases where the principles felt wrong or under-specified.
User-tagged The DEV user says "put this in the memo" mid-session. Virgil appends with full context.

Memo classes — three tiers

TierWhen writtenDream-phase treatment
unremarkableSkill ran cleanly. No friction. Default for routine invocations.Counted for statistics; not individually read.
notedVirgil hit a friction point, made a non-obvious choice, asked for help.Read individually; grouped by skill + bucket.
flaggedUser-tagged, or Virgil-confidence-low, or a Don't-rule almost got broken.Read first; may trigger fast-path if marked fix-now.

The dream phase

An overnight autonomous pass — triggered by a scheduled job or /loop /editor/dream on a long interval. Reads every memo since the last dream, synthesizes patterns, acts.

Two landing modes

Landing modeWhat qualifiesHow it ships
Acts directly Changes inside a single skill prompt that don't change behavior contracts: tighten a Don't-rule, add a clarifying example, fix a typo, expand guidance. Edits land in place on the main branch. Diff appears in the dream-digest with an "ACTED" tag.
Proposes via worktree Anything cross-skill, anything that changes a script, anything that touches the §3 manifest, any skill rename/merge/split, anything that changes a behavior contract. Dream runs in a git worktree. Proposed diff lives there with a "PROPOSED" entry in the dream-digest. User reviews before landing.

Fast-path memos

A memo marked flagged AND fix-now triggers an immediate single-memo dream pass — acts-directly only, narrow scope (single skill markdown file or single Don't-rule tightening). Anything more ambitious queues for the overnight run.

The bootstrap property

The dream phase is itself a Virgil skill, and the first dream phases will be the worst. So dream runs in DEV mode itself — it produces memos about its own performance just like every other skill. The next dream's input includes the previous dream's digest. Recursive but tractable; dream improves at dreaming over time.

Boundaries: dream cannot edit the architectural Don't-rules in editor/AGENTS.md, cannot modify the apply_response.py contract shape, cannot disable DEV mode itself. These are the load-bearing invariants that bound the self-improvement loop.

15. Forward-compatibility

v1 ships dev-dream only. A future version will add user-dream — per-user voice and preference learning that lives in an overlay outside the skill bundle's reach. v1 must preserve architectural optionality so that future version can land cleanly without rework. Five rules:

v1 forward-compat rules.
  1. Reserve overlay paths. ~/.virgil-user/ and <docpath>/.virgil/user-overrides/ are reserved namespaces from day one. The skill-bundle sync mechanism's deny-list excludes them in v1 — even though v1 never writes to either path, the sync code knows not to touch.
  2. Inbox preserves rejection-fidelity data. Every Task with result: rejected carries enough context (original text + proposed change) for a future learning loop to consume retroactively. v1 keeps completed Task rows indefinitely; no aggressive pruning.
  3. Skill prompts written for overlay-readiness. Base commandments stay as static rules in v1, phrased generally enough that future overlay-reading is a single-line addition: "these are the base rules unless your overlay specifies otherwise" — with the overlay clause being a no-op in v1 because the file is always absent.
  4. apply_response.py subcommands stay overlay-agnostic. No field in the subcommand contracts depends on a user-overlay existing. Adding overlay-write capabilities later doesn't break the contract.
  5. No revise-with-feedback skill in v1. Rejection signal flows through the natural Inbox path (result: rejected). When the user-dream layer lands, revise-with-feedback becomes the explicit "tell Virgil why you rejected" surface — but it's not in v1.

Concretely for v1 implementation:

  • The skill-bundle sync code has the deny-list (a few lines: "never touch paths starting with ~/.virgil-user/ or matching **/.virgil/user-overrides/**") — purely defensive against accidental future use.
  • Base revision commandments (when revision skills eventually land) are phrased as static text generally enough that adding "unless your overlay says otherwise" later is a single-line addition, not a rewrite.
  • v1 inbox retention is indefinite by default; archival mechanism is a separate future concern, not a default in v1.
  • v1 doesn't introduce revise-with-feedback in the skill set; users reject through the existing suggestion-card surface and the rejection lands as result: rejected on the Task.
