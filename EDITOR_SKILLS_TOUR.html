1. The shape of the inbox

Editor skills consume three intent surfaces, each writable by the user from a different part of the Virgil UI:

SurfaceWritten fromShape
virgil/ai-requests.json
the unified queue		 Toolbar "Ask Virgil" actions; the AI-request inbox panel Entries with kind ∈ {footnote, citation, quotation, note, todo, suggestion, style-merge} and status: draft | submitted | complete
Card-level aiRequest: true flags Notes, todos, cutter-comments, revision-comments panels Boolean toggle on the card. Bridged into the unified queue via bridgeCardAiRequestFlag(); legacy cards without a bridge entry appear as virtual:<panel>:<cardId> ids.
virgil/bib-review-requests.json Bibliography panel's "Review this entry" action Per-bib-key entries with type: "fields" | "notes". Stays separate because it's per-bib-key, not per-paragraph.

editor/scripts/list_requests.py walks all three and emits a unified JSONL stream with one shape:

{
  "source": "ai-requests | bib-review | card-flag",
  "kind":   "footnote | citation | quotation | note | todo | suggestion | style-merge | bib-review",
  "id":     "<request-id, bibKey, or virtual:panel:cardId>",
  "text":   "<user instruction>",
  "paragraphIds": [...],
  "selectedText": "<optional substring>",
  "linkedTo": { "panel": "...", "cardId": "..." },
  "extra":  { "status": "...", "createdAt": "...", "type": "fields|notes|...", ... }
}

2. The cowork loop

   Frontend                              Claude (separate session)
     │                                      │
     │  user files request ──►              │
     │   ai-requests.json /                 │
     │   bib-review-requests.json /         │
     │   aiRequest flag (→ bridged)         │
     │                                      ◄ /editor/review reads
     │                                      │   (via list_requests.py)
     │                                      │
     │                                      │   dispatches per-kind
     │                                      │   subskill subagent
     │                                      │
     │  <sidecar>.json (new card)        ◄ subskill writes via
     │  ai-requests.json (status flip)      apply_response.py:
     │  notifications.json (append)           • insert card
     │  version.txt (bumped)                  • flip status
     │                                        • clear source flag
     │                                        • append notification
     │                                        • bump version
     │                                      │
     ◄ useDocNotificationStream polls       │
       version.txt every 6s, refreshes      │
The one rule that organizes everything: the frontend never invokes Claude directly. It writes intent files; Claude drains them. apply_response.py is the only sanctioned writeback path — it owns the atomic card + status + notification + version-bump transaction.

4. The umbrella

umbrella/editor/review — Walk the unified inbox, dispatch each request to its specialist as a subagent.
Args
<docPath> (optional — falls back to cwd if it has a virgil/ subdir)
Reads
ai-requests.json (status != complete), bib-review-requests.json (status == pending), card-flag panels via list_requests.py
Writes
Nothing directly. Every write goes through the dispatched subskill.
Order
Strict: bib-review → style-merge → footnote → citation → quotation → note → todo → suggestion. Bib reviews and style merges go first so dependent work uses the updated state.
Subagent model
Each dispatch runs as a fresh subagent so context stays bounded. The umbrella prints a one-line dispatch log per request and continues on subskill failure.
Idempotence
Each subskill no-ops on status: complete — so a re-run after partial completion just picks up the rest.
Gotcha
On subskill failure the umbrella logs and continues. It does not block the queue. Look at notifications.json for any ai-request-failed entries after a drain.

5. Direct creates — insert into the paper without a suggestion wrapper. User can delete.

The three "insert it" skills

These create artifacts the user explicitly asked for (a footnote, a citation, a quotation). The result lands in place because the user already opted in by filing the request.

direct/editor/draft-footnote — Draft a footnote body, insert \vfid{uuid}\footnote{...} at the anchor in .tex, write a FootnoteRef card.
Args
<docPath> <requestId>
Reads
ai-requests.json, document.tex (via get_para_context.py), footnotes.json (tone), references.bib (to detect natbib vs biblatex)
Writes
  • document.tex — inserts the footnote anchor at the paragraph end or matching substring
  • footnotes.json — new FootnoteRef card via apply_response.py
  • ai-requests.json, notifications.json, version.txt — via apply_response.py
Decision
If paragraphIds is empty → halt with ai-request-failed notification, do not draft. If the request needs a bibkey not in references.bib → file a follow-up citation request rather than fabricating \citet{key}.
Idempotence
Skip if status != submitted.
Don't
  • Don't fabricate a \citet{} command for a citekey not in references.bib — file a follow-up citation request.
  • Don't include the trailing %!v:<uuid> paragraph marker in the .tex edit (it's auto-managed).
  • Always prepend a fresh \vcid{uuid} before every cite command in the footnote body.
  • Mode B (selectedText) requires exact substring match — fall back to end-of-paragraph on mismatch.

direct/editor/find-citation — Search Crossref / OpenAlex / Semantic Scholar / arXiv; add a BibTeX entry; create an unanchored CitationRef card the user drags into place.
Args
<docPath> <requestId>
Reads
ai-requests.json, document.tex (section context), references.bib (collision check + cite-command style detection), external bibliographic sources
Writes
  • references.bib — appends new entry, blank-line separated
  • citations.json — new CitationRef via apply_response.py
  • ai-requests.json, notifications.json, version.txt — via apply_response.py
Acceptance bar
DOI-verified, OR ≥2 independent authoritative sources agree. Hard bar — soft preferences in the user's request can't override it.
Decision
No source meets the bar → mark complete with a note explaining why; do NOT fabricate. Citekey collision → suffix with a, b, … never modify the existing entry.
Idempotence
Skip if status != submitted.
Don't
  • Don't use ISBN, LCCN, or publisher URLs as DOI field values — those go in their own fields or are omitted.
  • For article-number-only journals, set pages = {<article-number>} and omit number.
  • For disambiguation, read the existing entry's title field as the ground truth — not BibTeX type or journal name.

editor/skills/find-citation.md

direct/editor/draft-quotation — Assemble a QuotationGroup card nesting references, quotes, and anchor links.
Args
<docPath> <requestId>
Reads
ai-requests.json, document.tex, external sources if the user asked to find a quote (verbatim quotes use the user's text directly)
Writes
quotations.json + the usual apply_response.py trio (status flip / notification / version bump)
Decision
Empty paragraphIds → halt with ai-request-failed. Asked to find a quote but source isn't reachable → mark complete with a note. Never fabricate.
Don't
  • Never fabricate a quote. Verbatim or nothing.
  • page field: use the user's value verbatim; leave empty if absent — don't guess from metadata.
  • Quotes stay short (fair-use excerpt) — use the user's request as the upper bound.
  • Set notes: "" (required field), default margin.side: "left".

6. Card responders — work from a card the user already wrote; emit a sibling or a suggestion

The four "answer the user's flag" skills

These all start from a card the user authored (a note, a todo, a comment), interpret the AI flag on it, and emit a new sibling card — never editing the source. Each one has a fork between "you wanted a doc edit" (→ suggestion card) and "you wanted a response" (→ sibling).

responder/editor/answer-note-request — Answer a user note flagged for AI. Drafts a sibling note, or a suggestion card if the user asked for a doc edit.
Args
<docPath> <requestId> — may be virtual:notes:<cardId> for legacy un-bridged flags
Reads
notes.json, document.tex (paragraph context), adjacent cards via cards_for_paragraph.py
Fork
  1. Does the request ask to change document prose? → RevisionSuggestionCard in revisions.json.
  2. Else, is there a source note? → sibling note titled Re: <source-title>.
  3. Else → standalone note with a descriptive subject phrase.
Memo
Drops .virgil/memos/<YYYY-MM-DD>-answer-note-<requestId>.md only if it hit a real ambiguity worth surfacing.
Don't
  • Never edit the source note in place.
  • Never mutate document.tex from this skill (route through suggestion card).
  • aiOriginRequestId: only include it if <requestId> doesn't start with virtual:.

editor/skills/answer-note-request.md

responder/editor/answer-todo-request — Classify a heterogeneous AI-todo as a text-edit (→ suggestion), missing artifact (→ follow-up request), analysis (→ sibling note), or limit (mark complete).
Args
<docPath> <requestId> — may be virtual:todos:<cardId>
Reads
todos.json, document.tex
Four-way fork
  1. Text-edit: emit RevisionSuggestionCard with status: pending. Leave the todo's done: false — the user accepts via the suggestion card.
  2. Missing artifact (footnote / citation / quotation): file a follow-up ai-request entry of the right kind; mark the todo's request complete.
  3. Analysis / answer: emit a sibling note; flip done: true on the source todo.
  4. Limit / impossible ask: mark complete with a note. Flip done: true.
Don't
  • Don't guess at the todo's intent — when ambiguous, mark complete with a clarification note.
  • Exclude the trailing %!v:<uuid> from original_text on suggestions — accept-time replacement must not delete the marker.

editor/skills/answer-todo-request.md

responder/editor/answer-cutter-comment — Respond to a flagged comment on a cut/excerpt in the Cutter panel. Always emits a CutterSuggestionCard.
Args
<docPath> <requestId> — typically virtual:cutter:<cardId>
Reads
cutter.json, document.tex, adjacent cards
Writes
New CutterSuggestionCard in cutter.json + standard apply_response.py writeback
Fork
None. Always emits a suggestion with status: pending.
Don't
  • original_text must be verbatim from .tex — the editor uses it as the accept-time search key.
  • Copy anchor.paragraphIds and anchor.margin from the source comment's first link.
  • target.ref is self-referential: kind: "suggestion", id: <new-card-id>.
  • instructions carries the source comment's text for replay-on-redo.
  • Empty suggested_text means "cut entirely" — appropriate if the comment asks for a cut, otherwise propose a replacement.

editor/skills/answer-cutter-comment.md

responder/editor/answer-revision-comment — Respond to a flagged comment in the Revisions panel. Sibling comment, or a suggestion card if the user asked for a doc edit.
Args
<docPath> <requestId> — typically virtual:revisions:<cardId>
Reads
revisions.json, document.tex, adjacent revision cards
Fork
Doc edit? → RevisionSuggestionCard. Else → sibling RevisionCommentCard.
Idempotence
Skip if a sibling reply with matching aiOriginRequestId already exists.
Don't
  • Never edit the source comment.
  • Never mutate document.tex — even on the suggestion path, the card carries the proposed replacement.
  • original_text must be verbatim, and must exclude the %!v:<uuid> marker.

7. The "always a suggestion card" case

This one is interesting: it's invoked directly (not via a card flag), but unlike the other direct-creates it always wraps output in a suggestion card. That's because the user is asking for a rewrite, and rewrites need approval.
directsuggestion-only/editor/draft-suggestion — Propose a revision to a paragraph. Always emits a RevisionSuggestionCard with author: "ai", status: "pending".
Args
<docPath> <requestId>
Reads
ai-requests.json, document.tex
Writes
New RevisionSuggestionCard in revisions.json + standard writeback
Hard rule
Does NOT edit document.tex. Always goes through a suggestion card the user accepts or rejects.
Don't
  • original_text MUST match the .tex byte-for-byte; accept-time uses it as the search key.
  • Include \vcid{...} and inline LaTeX verbatim — don't invent fresh UUIDs.
  • Exclude the trailing %!v:<uuid> marker comment.
  • Treat negative constraints in the user's request ("too many em-dashes when there are none") as instructions not to introduce, not blockers to the rewrite they actually wanted.

8. Bibliography

Two skills, very different scopes

answer-bib-review works on a single entry (three modes). sync-bib-to-library reconciles the whole paper against the user's Virgil Library and cross-cuts into library writes — the only editor skill that does so.

bib/editor/answer-bib-review — Three-mode skill: verify/fill fields, draft an annotation, or swap a library entry in.
Args
<docPath> <bibKey> [--library-sync <libraryCitekey> --library <path>]
Three modes
  1. type: "fields" — verify the entry's fields against Crossref / OpenAlex / Semantic Scholar / arXiv; replace verified, leave unverified as-is with a status note. If lookup contradicts the entry's BibTeX type, fix the type and reshape the field set.
  2. type: "notes" — draft an annotation note (in annotations.json) summarizing the source.
  3. --library-sync — short-circuit modes 1-2 and swap in the library's authoritative entry. Uses rename_citekey.py to rewrite every \cite*{...} command if the library citekey differs from the paper's.
Writes
references.bib, annotations.json (notes mode), document.tex + citations.json (rename), bib-review-requests.json (status flip)
Idempotence
Re-running on an already-synced entry is a no-op (entry bytes don't change).
Don't
  • Don't fabricate fields. Unverified fields stay as-is with a status note.
  • If a DOI can't be added (common for pre-2000 works), declare that explicitly instead of fishing.
  • Script-path resolution: walk .virgil/scripts/editor/ and editor/scripts/ to find helpers; don't hardcode.

bibcross-cut/editor/sync-bib-to-library — Reconcile a paper's whole bibliography against the user's Virgil Library: matched → swap to library form (+ rename citekeys throughout doc); missing → triage into library; ambiguous → review note.
Args
<docPath> [--dry-run] [--library <path>]
Reads
references.bib, document.tex, citations.json, library's master.bib, library's .virgil/catalog.json
Match phases
  1. Matched (by citekey, DOI, or title+author signature) → swap entry via answer-bib-review --library-sync
  2. Missing → bundle, triage into library's unsorted/ via triage_apply.py, authenticate per citekey, re-match, swap
  3. Ambiguous (signature hits multiple library candidates) → write a review note listing candidates; do NOT auto-swap
Cross-cut safety
All library writes go through flock-protected CLI shims (update_master_bib_entry.py, triage_apply.py) — safe to interleave with a parallel /loop /library/index-pending in another session.
Idempotence
Re-running on a fully-matched bibliography is a no-op: pass 1 hits 100% matched, pass 2 has nothing to triage, no ambiguous note.
Don't
  • Don't auto-swap on ambiguous matches. Write the review note and leave the paper's entry alone.
  • Trust library terminal states. bib.state ∈ {failed, unverified, manuscript, canonical} are authoritative — don't try to "fix" them from the paper's side.
  • Don't delete entries from references.bib that aren't in document.tex. Some users keep an extended bibliography.
  • If a bib-system swap (natbib ↔ biblatex) is detected, flag it loudly — user must manually swap the body markers (\bibliography{} vs \printbibliography).

9. Style

style/editor/style-merge — Merge the user's preamble customizations onto a new target style's preamble. Rewrites .tex; body untouched.
Args
<docPath> (optional — prompts if omitted)
Reads
ai-requests.json (kind=style-merge, status=submitted), document-settings.json (current styleId), document.tex (preamble + body split)
Writes
document.tex (preamble rewrite), document-settings.json (styleId update), ai-requests.json (status flip), notifications.json, version.txt
Carries forward
  • \usepackage{...} (with options)
  • \newcommand / \providecommand / \renewcommand / \DeclareRobustCommand
  • \setlength / \setcounter
  • font-config directives
Drops
  • \providecommand{\vfid} / \vcid / \vexid (auto-injected at serialize time)
  • \title / \author / \date (re-injected at serialize time)
  • \documentclass (target owns it)
  • Shadowed bib packages (natbib vs biblatex)
Validation
Exactly one \begin{document}, no \end{document}, matched braces. On validation failure → mark request complete with a resultId describing the failure; do NOT write the .tex.
Don't
  • Never write if body extraction returns empty. Signals a corrupted source file.
  • Merged preamble must end with \begin{document}\n\n exactly.
  • On bib-system swap, flag loudly — user must fix the body markers manually.

10. Dev meta

dev-only/editor/iterate-virgil-editor — Stress-test and refine the editor skill set in sandboxed copies of the sample paper. Synthesizes requests, runs target skill via subagents, reads critique memos, edits skill markdown, loops.
Args
[<skill-name>] [<max-attempts>] — defaults: all skills in dependency order, 12 attempts (max 20)
Reads
editor/skills/<skill>.md, samples/annotation-history/ (never mutated — cloned per attempt)
Writes
  • editor/dev/sandboxes/<date>-<skill>-<case>-attempt<k>/ — per-attempt clones (gitignored)
  • editor/dev/iterations/<date>-<skill>/<case>-attempt<k>.md — critique memos from runners (gitignored)
  • editor/skills/<skill>.md — edits applied by loop driver between attempts
Per-skill loop
3-5 test cases (happy path, missing context, Mode B, underspecified ask, cross-skill edge) × 4 attempts per case. Runner subagent executes the target skill against a fresh sandbox; loop driver reads the critique memo, applies [block] edits, re-runs.
Survey pass
Every 3 skills stabilize → a cross-skill drift check.
Don't
  • Never mutate samples/annotation-history/ directly. Sandbox-only.
  • Never commit. Loop ends with diffs in the working tree for user inspection.
  • Runner subagents never edit editor/skills/. Only the loop driver does.
  • Rebuild the bundle after all edits: npm run build:editor-bundle.

11. Plumbing

Every skill writes through the same atomic writeback path. Understanding these three files explains why the skills are so terse:

editor/scripts/apply_response.py

The single sanctioned writeback. Owns the atomic card + status flip + source-flag clear + notification + version-bump transaction.

Op shape:

{
  "requestId": "<real id or virtual:p:id>",
  "panel": "notes|todos|cutter|revisions|
            footnotes|citations|quotations",
  "card": { ...full card... },
  "summary": "<one-liner>",
  "clearSourceFlag": true/false
}

Modes:

  • Apply — insert card, flip request, clear flag, notify, bump.
  • Complete-only (--complete-only <id>) — flip status without a card. For bib reviews and failures.
  • Revert (--revert <id>) — remove card, reopen request.

editor/scripts/list_requests.py

Emits the unified JSONL inbox. Three sources fan into one shape (see §1).

Virtual ids are the key trick: legacy un-bridged card flags appear as virtual:<panel>:<cardId>, so /editor/review can dispatch them through the same routing table as real ai-requests. apply_response.py recognizes the prefix and clears the source flag instead of touching ai-requests.json.

editor/scripts/_common.py

Stdlib-only helpers: resolve_doc, find_tex_file, find_bib_file, read_json / write_json, find_paragraph_uuids, card_paragraph_ids, append_notification, bump_version, now_iso, die.

Bridge: bridgeCardAiRequestFlag()

Lives in src/lib/ai-request-bridge.ts. When a user toggles aiRequest: true on a note/todo/cutter-comment/revision-comment, this hook adds an entry to ai-requests.json with linkedTo: { panel, cardId }. Toggling off removes the entry; toggling back on re-adds with fresh paragraph context. Collapses three discovery paths into two so /editor/review only needs to walk two files.

Library-path resolution

For the one cross-cutting skill (sync-bib-to-library) and the --library-sync mode of answer-bib-review:

  1. --library <path> flag
  2. VIRGIL_LIBRARY_ROOT env var
  3. ~/.config/virgil/library-path.json
  4. ~/Virgil-Library/ (legacy default)

Each candidate is validated against the master.bib + .virgil/catalog.json + .virgil/scripts/ triple — stale records fail loudly. Set centrally with:

python3 editor/scripts/library_path.py --set /absolute/path/to/library

12. House conventions

  • Reply format: one-line Done: <action> for <id>. Output: <files>.
  • Idempotence: re-running on status: "complete" is always a no-op.
  • Suggestion-card default: ambiguous responders emit suggestion cards with author: "ai", status: "pending" — never edit in place.
  • Direct-create kinds (footnote, citation, quotation) insert without a wrapper. The user opted in by filing the request; they can delete if unwanted.
  • Memo discipline:
    • Dev memos under <docPath>/.virgil/memos/<YYYY-MM-DD>-<slug>.md — only when an ambiguity is worth surfacing.
    • Paper-specific reports under <docPath>/notes/<slug>.md.
    • Never drop a markdown file at the doc root.
  • Path resolution for all skills:
    1. Explicit <docPath> arg.
    2. cwd if it has a virgil/ subdir.
    3. Error.
Three don'ts the editor AGENTS.md calls out:
  1. Don't write to document.tex from a Python helper. Skills do .tex edits with the Edit tool so they go through the same write-queue surface as user edits.
  2. Don't bypass apply_response.py for the writeback. Even when the op shape isn't a perfect fit, route through it (or extend it).
  3. Don't add a backend. The cowork pattern is load-bearing.
