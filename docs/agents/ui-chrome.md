# UI Chrome

Structural map of everything surrounding the main text editor: strips, panels, toolbars, and the orchestrator that wires them together.

See `glossary.md` for user-term ↔ code-name mapping.

## The orchestrator (post Path A 7.8)

The orchestrator role is now split across two files:

- **[src/components/EditorLayout.tsx](../../src/components/EditorLayout.tsx)** (~3820 lines, shrank further when the detached-toolbar tear-off arrays were deleted — see MenuBar section below — and when the topbar was extracted into memoized `TopBar` / `TabStrip` / `StatusCluster` sub-components under [editor-layout/](../../src/components/editor-layout/)) — the **shell wrapper**. Owns tab/file management (`useFiles`), `useViewPrefs` ownership (handed to EditorPane via `viewPrefs` prop), the Virgil bar and its DocTab/LibraryTab strip, the `activePane` switch (paper / library-outer / doc routing), top-bar dialogs (Preferences, Fonts, Margins, NewDoc, TexFilePicker, DocumentClassMismatch, ManageStyles), the PDF view branch, and the Code view. The topbar's status surfaces (collab pill, external-change badge, `PreservationNoticeBadge`, `SkillSyncControls`, Style / Print / Compile / PDF buttons) now live in the extracted `StatusCluster` ([editor-layout/StatusCluster.tsx](../../src/components/editor-layout/StatusCluster.tsx)); the doc/library tab strip in `TabStrip` ([editor-layout/TabStrip.tsx](../../src/components/editor-layout/TabStrip.tsx)). Per 8b9659c, Code view is now a draggable **split-pane alongside EditorPane** ([split-with-code.tsx](../../src/components/editor-layout/split-with-code.tsx) + `CodePaneSplitContext`), not a full-screen replacement; the `CodeEditor` (CodeMirror) state still lives in EditorLayout and code↔TipTap edits sync through [code-pane-bridge.ts](../../src/lib/code-pane-bridge.ts) (TipTap stays canonical). The vestigial `detachedActions[]` / `detachedFormatting[]` / `detachedMenus[]` tear-off arrays + their body-portal renders are **deleted** in both files — the action vocabulary now lives entirely behind the registry-backed menus (see MenuBar / SelectionActionsMenu sections below).
- **[src/components/EditorPane.tsx](../../src/components/EditorPane.tsx)** (~8200 lines) — the **canonical editor surface** mounted by both the main app's doc branch (from EditorLayout) and the Library Reader (from `library/components/PaperRender.tsx`). EditorPane owns per-doc hooks (`useDocument`, `useLatexCompile`, `useNotes`, `useTodos`, `useCitations`, `useCollab`, `usePristineCardManager`, …), the docked `MenuBar` (now inside the in-card chrome header, ~line 6460 — see MenuBar section), the panel rail (`PaneRail` left + right), the floating-panel block, and the canonical `DockOutline` (~line 5719) / `CardLiftOutline`.

When anything touches UI layout, chrome, or panel placement: if it's a tab/dialog/Virgil-bar concern → EditorLayout; if it's a per-document chrome / panel / popout / MenuBar concern → EditorPane. The full split is documented in `architecture.md` → "EditorPane vs EditorLayout".

The two bundles flow shell→pane, and **both** surfaces now pass BOTH (F#16, 0bdb1c90):
- `viewPrefs: EditorPaneViewPrefs` — dock/float-shaped state. The main app builds it from the persisted `useViewPrefs()`; the Reader gets it from `useReaderView(editor, editorHandleRef, scrollEl)` (which runs the same `useViewPrefs` engine in `"ephemeral"` session-only mode), both assembled by the shared `buildEditorPaneViewPrefs(...)` builder ([build-editor-pane-view-prefs.ts](../../src/components/editor-layout/build-editor-pane-view-prefs.ts)). So the rail, dock, float, and omni machinery is LIVE in the Reader too; the only Editor/Reader delta is the named `EditorMutationHandlers` set (most no-op in the read-only Reader, but `onScrollToHeading` is real).
- `menuBar: EditorPaneMenuBarBundle` — toggle state, para-nav, dialog openers (Fonts…/Margins…). The Reader now ALSO passes one: `useReaderView` returns both bundles off ONE ephemeral `useViewPrefs` instance (so a View-menu toggle and a panel-rail click mutate the SAME store), so the docked MenuBar lights up in both reader contexts (inline panel + outer tab). The Reader's View toggles (par titles, latex comments, heading labels, marginalia/highlight types, divider levels/width, dim-at-rest, close-all) and paragraph back/forward (via the keystroke-safe wall-clock `useParaNavHistory`) are functional; Fonts…/Margins… auto-drop via `READER_CHROME.showMenuBarEditItems=false`.

The `chrome` prop ([chrome-config.ts](../../src/components/editor-layout/chrome-config.ts)) gates feature visibility per surface: main app passes `FULL_CHROME`, Reader passes `READER_CHROME`.

## Tool strips (left & right)

Rendered by `IconStrip` (inside `PaneRail`) in `EditorPane.tsx` (~line 7412 for `data-strip-side`). Identical structure on both sides:

1. **View control pod** (grouped buttons at top):
   - Collapse/expand sidebar
   - Omni-view toggle (`toggleOmniHideAllCards`; `IconBlank` — show all omni-eligible panels, or blank)
   - (The **Split panel toggle is retired** — panels now stack as bands over an always-on omni, see "Panel column" below.)
2. **Panel icon buttons** — one `StripButton` per panel assigned to this side:
   - Icon color-coded to panel theme (from `PANEL_ICONS` in [src/components/editor-layout/panel-icons.tsx](../../src/components/editor-layout/panel-icons.tsx))
   - Click toggles open/closed
   - Draggable: drag to reorder, or drag across strips to move panel to the other side
   - Badge support (e.g. Revisions shows count when > 0)
3. **`OmniFilterMenu`** — horizontal kebab pinned to the bottom via `mt-auto`. Opens a dropdown that toggles which omni categories appear in this side's omni-view. Includes a "Default view" item that resets the side's hidden set. Since task 381 a category's COLUMN is DERIVED from the live strip side of the panel that owns it (`resolvePanelSide` over `prefs.placements`) rather than stored — `registry.omniSide` and `DEFAULT_OMNI_CATEGORIES` are deleted, and the stored fact is side-free VISIBILITY (`prefs.omniHiddenCategories`, a hidden SET, so a newly omni-eligible panel is visible by declaration with no migration). The two facts combine once in [src/panels/Omni/omni-categories.ts](../../src/panels/Omni/omni-categories.ts) (`omniCategoriesForSide`), a light leaf `useViewPrefs` + the Reader's derivation can read without pulling the React component. Menu lives in [src/panels/Omni/OmniViewPanel.tsx](../../src/panels/Omni/OmniViewPanel.tsx).

`StripButton` lives in [src/components/editor-layout/drag-drop.tsx](../../src/components/editor-layout/drag-drop.tsx).

Panel-side assignment is stored in `prefs.placements` and defaults come from `defaultStripSide` in `PANEL_REGISTRY`.

## Panel column

[src/components/editor-layout/panel-column.tsx](../../src/components/editor-layout/panel-column.tsx) — `PanelColumn` (also exports the `BandSpec` type and `measureOmniGap`).

**Auto-stacking band layout (51e0092).** The single-slot/split model is gone. The column is an always-mounted omni "desktop"; up to `MAX_STACK` opaque content-sized **bands** stack top→bottom over it. Three layers inside the column root: (A) `{omni}` in normal flow (the background); (B) an absolute pass-through layer so empty gaps click through to omni; (C) a sticky stack frame holding the band anchors (`data-dock-slot` keys, top→bottom) with a `BandDivider` ([panel-primitives.tsx](../../src/components/panel-primitives.tsx)) between consecutive bands. Each band anchor is empty — `<FloatingPanel mode="docked">` portals its panel content into the anchor, visually covering omni (which stays mounted underneath). When `stack` is empty the column is omni-only. (The Reader can now dock bands too — it runs the same ephemeral `useViewPrefs` engine — so its stack isn't always empty.)

Props: `side` ("left"|"right"), `panelPref` / `onPanelPrefChange` (column **width**), `isResizing` / `onResizingChange`, `onSyncBeforeDrag`, `omni` (the always-mounted desktop node), `stack: BandSpec[]` (ordered bands top→bottom, each `{ id, height? }`), `onTradeHeight` (divider drag, trades px height between two adjacent bands), `onResizeBottomEdge` (bottom-band edge drag — reveals/covers the omni gap), `onFocusBand` (MRU bump), `collapsed`, optional `tail`.

- The dock stack lives in `prefs.dockStack[side]` (replaces `dockSlots`); per-band height in `prefs.panelHeights`. Strip-click open appends a band at the bottom, evicting the LRU band when there's no room — gated by `measureOmniGap(side)` (a one-shot read of the live gap below the docked stack; no observers).
- The bottom band carries a **bottom-edge resize handle** with a visible **grip slider** (`.band-grip`, opaque manilla backing that fades into omni when it's the only band — a17b9e9/464092a/e6442ca). `BandDivider` does the same for the boundary between two stacked bands. Docked bands flex-fill so a tall band caps + scrolls instead of running off (5831ad4). Every divider gesture in the app — band dividers, the bottom-edge handle, panel-column width, the code splitter, zen margins, the Library gutters — runs on the ONE pane-resize engine ([src/lib/pane-resize/](../../src/lib/pane-resize/): `usePaneResizeHandle` + the edge-only `LayoutGestureBus` + the `PaneFreeze`/`parkDuringLayoutGesture`/`useLayoutGestureActive` gesture-time followers — the bus also carries the OS window resize, so a follower parks for both gestures), with `.band-grip` as the shared grip chrome; doctrine in AGENTS.md "Pane-drag stability" + "Layout-gesture stability" + STYLE_GUIDE "Resize gutters".
- **The pod seam** (tasks 329 / 329b). Where a raised white pod's bottom edge meets the card lane continuing behind it, the separation reads as *elevation* — the pod's own ambient shadow falling across a thin canvas strip — not as a band of empty desk. `--pod-seam` (globals.css) owns that width and is DERIVED: the greatest downward reach of `--card-shadow-ambient`, rounded up (6px). It is a distinct question from `--pod-gap`, which is the resize strip / column inset; the two were conflated, spelled three ways in one file, and where two spellings met they SUMMED into the ~44px "moat" Gabriel reported. The grab target is the REACHABLE half of the seam, not its nominal box. Rationale + the contract test: STYLE_GUIDE → "The pod seam".
- Width: inner-edge drag adjusts this column's **panel preferred size**; the editor column (high flex-grow) absorbs the change. Clamped by `--panel-min` and the editor's min-width. `onSyncBeforeDrag` snaps prefs to rendered widths before the drag. Collapses to zero width when `collapsed`.

Panels render via `<PaneRailBody>` inside EditorPane. The same panel components are used for rail-mounted and floating variants (floating wraps in `FloatingPanel`).

## Panels

All panels share the wrapper system in [src/components/panel-primitives.tsx](../../src/components/panel-primitives.tsx) and [src/panels/_shared/](../../src/panels/_shared/). Two wrapper shapes:

- **`Panel`** — universal outer. Flex column with header (whose trailing slot is the close X) and scroll body. Used by panels with custom bodies (Outline, Search, WordCount).
- **`CardListPanel<T>`** — wraps `Panel` + iterates items as cards + adds AI-requests section. Used by card panels. Its header badge is **derived from the set it actually renders** (post-filter), not passed in — the `count` prop was removed in task 183, so the badge can no longer disagree with the rows beneath it. (The historical list/in-text view-mode toggle and `panel-view-mode` context were removed; cards now always render in list form.) It also applies the **per-card archive view filter** (`filterByArchiveView` in [src/panels/_shared/card-archive-view.tsx](../../src/panels/_shared/card-archive-view.tsx)) — see "Per-card archive" below.

**Header** is `PanelHeader` — fixed 26px (`--header-h`), slots in order: `leading`, title + count, `titleAfter`, optional `onAdd`/`onAddOptions` (+ icon), `children` (extras), and a trailing `PanelClose` X. There is no AI-request slot in the header — AI requests are per-**card** (`AiRequestCheckbox`).

### Panel list

See `glossary.md` for the full table. Quick reference: 11 card panels (`notes`, `footnotes`, `citations`, `bibliography`, `reports`, `examples`, `todo`, `archive`, `revisions`, `cutter`, `errors`) and 4 non-card panels (`outline`, `search`, `wordcount`, `omni`). **Notes, Reports, Revisions, and Cutter are polymorphic** (two card kinds each). Notes: `note` + `highlight` (registry `card: null`); Reports: `report` + `report-request` (`card: null`); Revisions: `revision-comment` + `revision-suggestion` (registry `card.kind` is `revision-comment`); Cutter: `cutter-comment` + `cutter-suggestion` (`card: null`). Panel membership for each kind derives from `CardMeta.panel` in `CARD_REGISTRY` via `cardKindsForPanel` (the hand-kept polymorphic-panel table was retired in 27458d8). The Revisions panel additionally tracks a per-document "revisions accepted" counter (`RevisionsTracker`); the Cutter panel tracks a word-count goal (`CutterGoal`). Both render through ONE `PanelGoalStrip` (task 286 — `CutterGoalStrip` and `RevisionsTrackerStrip` were hand-forked twins; parity pinned by `panel-goal-strip-parity.test.tsx`), and the STYLE_GUIDE's `bg-emerald-*` ban is now a CI census rather than unenforced prose.

Omni-eligible panels (shown in Omni view): notes, footnotes, citations, reports, examples, todo, archive, **revisions**, **cutter**, **errors**. Bibliography is the only card panel that's *not* omni-eligible.

**Omni bins (tasks 421–422).** A card omni cannot place in the cascade is surfaced in a collapsed **bin pill** at the head of the column — one pill per state, all three rendering through the ONE `OmniBinPill` primitive: **"N unanchored"** (error tone, `BadgeOrphaned` — the same word/badge/set as the pane-chrome `UnanchoredCardsChip`, differing only by side and filter scope), **"N unplaced"** (neutral — a `free` card, deliberately parked, which is a normal state and gets no red badge), and **"N outside focus"** (neutral). The split follows the `AnchorState` SSOT: summing `free` + `orphaned` into one error-toned pill made one word name two sets on screen at once. `tone` is a REQUIRED prop (published as `data-omni-bin-tone`) so a new bin can't inherit an error look by default. **Placement**: the bins live in the column's ONE sticky layer, not the document-tall cascade pod — `PanelColumn` renders an empty slot as the last flex child of the band frame (Layer C) and publishes it through [omni-bin-slot.ts](../../src/components/editor-layout/omni-bin-slot.ts); `OmniViewPanel` portals its `OmniBinStack` into it. So the bins stack BELOW whatever bands are docked by flex order rather than a z-index race, are sticky for free, and take zero flow space in the pod. With no column host (unit fixtures, a bare mount) the stack falls back to an in-pod sticky posture.

Omni-view surfaces a **`OmniBulkPendingHeader`** when applied-pending changes exist: since 209eac4d it's a **navigator** — `[▲ prev] [counter "i of N"] [▼ next] … [⋮]` — where ▲/▼ step the applied changes in doc order (scroll-into-view + light the blue range, via `sortAppliedKeysByDocPos` in [pending-change-nav.ts](../../src/links/pending-change-nav.ts)) and the ⋮ kebab holds Keep-all / Dismiss-all (was a flat count + Keep-all/Dismiss-all strip). **It renders on ONE side, chosen by PLACEMENT (task 420):** `appliedPendingSide(categorySides)` ([omni-categories.ts](../../src/panels/Omni/omni-categories.ts)) resolves the side from the derived category placements (the task-381 ladder), with the family set derived from `APPLIED_SPLICE_KIND_LIST` and a stated tie-break (first family → Revisions). The old per-host gate was a per-side VIEW-FILTER predicate, so Revisions and Cutter on opposite strips gave two navigators driving one cursor, and hiding both in the filter menu removed the only document-wide way to find/keep/revert unreviewed applied AI text while the blue ranges stayed live in the `.tex`. Placement decides WHERE; visibility decides nothing.

Each omni-eligible panel owns its own `omni.tsx` next to the panel (e.g. [src/panels/Cutter/omni.tsx](../../src/panels/Cutter/omni.tsx), [src/panels/Errors/omni.tsx](../../src/panels/Errors/omni.tsx), [src/panels/Revisions/omni.tsx](../../src/panels/Revisions/omni.tsx)) exporting a `buildXOmniItems(args): OmniItem[]` builder. The orchestrator-side host [src/components/editor-layout/panels/omni-host.tsx](../../src/components/editor-layout/panels/omni-host.tsx) imports each builder and concatenates the results into the per-side omni columns. New omni-eligible panels add their builder there.

### Per-card archive

A per-card **archive** affordance (distinct from the text-object **Archive panel** and from the `Archive` *action* that creates archive cards) lets the user set an individual card aside. Each card carries its own `archived` flag; archived cards hide from active panel views, the in-text margin markers, and omni.

- **Predicate**: `isArchivable(kind)` ([src/cards/predicates.ts](../../src/cards/predicates.ts)) — true for user-authored kinds EXCEPT `highlight` (delete-only, user decision). `footnote` joined the archivable set in bug sweep #3 (mirror of citation). `archiveRemovesAtom(kind)` (= the inline-atom predicate) is true for citation **and footnote**: archiving splices the `\cite{}`/`\footnote{}` atom out of the `.tex` behind a confirm, and unarchiving does NOT re-insert it (card returns as an unanchored ref, listed under the panel's Archives view).
- **Button**: `CardArchiveButton` ([panel-primitives.tsx](../../src/components/panel-primitives.tsx)) — hover-revealed, just left of `CardTrashButton` at the card's bottom-right; flips to an "Unarchive" restore glyph when archived. For cards whose delete lives in the header three-dot menu, `MenuArchive` is the menu-item sibling of `MenuDelete`.
- **Wiring**: `EditableCard` self-wires the affordance from the `CardArchiveActionsApi` context ([src/panels/_shared/card-archive-actions.tsx](../../src/panels/_shared/card-archive-actions.tsx)) — `enabled` (false in Reader / tests) + `isArchived(id)` (stable-identity ref read, so a body keystroke never re-renders every card) + `archive(kind, id)`. EditorPane provides it from its single `useViewPrefs`.
- **View menu**: `CardViewModeMenuItems` ([src/panels/_shared/CardViewModeMenu.tsx](../../src/panels/_shared/CardViewModeMenu.tsx)) drops a **View Active / View Archives / View All** radio section into each card panel's header three-dot menu, reading/writing the shared card-archive-view context via `useCardArchiveView()` ([card-archive-view.tsx](../../src/panels/_shared/card-archive-view.tsx)). `CardListPanel` filters its rows by that mode via `filterByArchiveView`. State: `prefs.cardArchiveView` (per panel kind) on `useViewPrefs` (`setCardArchiveView`). `prefs.suppressArchiveAtomWarning` is **RETIRED** (task 492): the atom-archive confirm's "don't ask again" was three hand-rolled copies of one idea in one caller (a pref field, a checkbox hand-authored inside the dialog's `message`, a gate at the call site), so the capability moved onto the confirm DOOR — a confirm opts in with one `suppressId` and the answer is now GLOBAL rather than per-window. See "Dialogs" below. The empty body is **view-aware** (task 478): `ArchiveViewEmptyState` ([src/panels/_shared/ArchiveViewEmptyState.tsx](../../src/panels/_shared/ArchiveViewEmptyState.tsx)) names the VIEW rather than saying "No tasks yet. Click + to create one" over twelve live cards, and the copy lives beside the renderer while the RULE (`ArchiveEmptyReason`) stays in the import-light `card-archive-view.tsx` leaf. `OmniHost` reads the SAME cross-panel `archivedIds` set the margin markers and the unanchored chip read, and applies it ONCE to its ASSEMBLED item array via `filterArchivedOmniItems` ([src/panels/Omni/omni-archived.ts](../../src/panels/Omni/omni-archived.ts)) — task 476 retired the per-builder derivation (a local `active()` helper covering six of ten families, a private gate inside the footnote builder, and citations covered by neither, so an archived citation lived in the "N unplaced" bin forever). The prop is REQUIRED; no `omni.tsx` may spell `archived` itself. See AGENTS.md → "The archived half".

## Bar occupancy (several residents, ONE priority rule)

The Virgil bar is a fixed-width strip with three occupants — protected status, the tab row, and the collapsible tool group — and before task 395 they did not negotiate: `TabStrip` was `flex-1 min-w-0` while every tab inside it was `shrink-0` with no clip, so at a narrow window the tabs simply spilled RIGHT and the tool icons painted across the active tab's label. (`TopBar`'s own comment promised a clamp against a "topbar-left sentinel" that had no element and no consumer — the mechanism was real once, moved into the pod chrome header, and the prose outlived it by two months.)

The ladder is stated once in [bar-occupancy.ts](../../src/components/editor-layout/bar-occupancy.ts) — **protected status > tabs > collapsible tools** — and resolved by `useBarOccupancy` ([useBarOccupancy.ts](../../src/components/editor-layout/useBarOccupancy.ts)) from ONE ResizeObserver over three boxes. Under it sits a structural FLOOR: the tab strip clips its own horizontal overflow (`overflow-x: clip` / `overflow-y: visible` — `hidden` would coerce the vertical axis to `auto` and eat the active tab's seam overhang), so an overlap is unrepresentable rather than merely avoided. Four rules worth knowing:

- The predicate is **state-independent**, so it needs no hysteresis: the strip's assigned box already nets out the protected width and (while expanded) the tools, so "does it fit?" reduces to the same inequality in both states. Written naively — *do the tabs overflow their box?* — collapsing frees room, the tabs then fit, the rule expands, and it re-collapses forever.
- It runs **live during a layout gesture** (the `useWindowChrome` exemption in AGENTS.md → "Layout-gesture stability"): parking the verdict means the bar visibly overlaps for the whole of an OS window drag, which is the defect. Cost is three post-layout `contentRect.width` reads behind a per-role equality bail; a whole resize drag commits ONE React render, at the crossing.
- The rule governs the **default**; the user outranks it. The auto rule never writes the persisted `topbarRightCollapsed` pref, and an expand out of an AUTO collapse mints a session override that is dropped on the auto TRUE→FALSE edge — minted from `autoRef.current`, never a bare `true`, since an override created while nothing was crowding would have no expiry and would disable the rule for the session.
- **Nothing in a higher tier may change width as a function of the verdict**, or state-independence is false. That is why `SaveStateBadge` reads the user's `collapsePreference` and not the effective value.

The collapsible group collapses by **width, not by unmounting**, which is what keeps the measurement available in both states — and leaves three debts paid on the collapse edge: the children are REMOUNTED (a `key` on the inner content, never on the measured wrapper) so body-portalled dropdowns close, focus moves to the chip (tracked as focus-WITHIN, since `activeElement` has already fallen to `<body>` by the time an effect can ask), and the clip is CONDITIONAL so an expanded button's focus ring isn't trimmed. A composed ref on a measured element must be a **stable** `useCallback` — React detaches an unstable ref callback on every render, and this one's detach drops the strip's measurement. CI: `bar-occupancy.test.tsx` drives the REAL `TopBar` through a fake `ResizeObserver` (jsdom has no layout, so what is measurable is the DECISION, not the boxes) plus a census of the clip pair and the shared label cap. **Residual:** the floor CLIPS and offers no overflow affordance — a tab row still wider than the strip after the tools have yielded loses its rightmost tabs silently, and the paper-drop indicator is invisible past the boundary (the drop INDEX still commits correctly).

## Margin chrome geometry (block-frame)

[src/text-objects/block-frame.ts](../../src/text-objects/block-frame.ts) is the **one canonical per-block geometry source** for every margin affordance (per the #51 gutter→margin rename, the code calls these "margin affordances"). `resolveBlockFrame(el)` returns a `BlockFrame` (viewport coords): `opticalCenterY` (cap-band center of the first visual text line — the vertical anchor), the horizontal `contentLeft` / `contentWidth` / `contentRight` content edges, a MEASURED `markerLeft` (the block's leftmost marker glyph — bullet band / `(n)` / `a.` / plain text), and an em `gapPx` resolved against the block's font. `resolveContentEdges(el)` is the lean horizontal-only primitive that `resolveBlockFrame` composes, so a full frame and a direct edges call can never diverge. Resolution is pure DOM + ancestry — O(1)/O(depth), never a doc walk (keystroke sanctity), safe on the hover/scroll/RAF placement and throttled-mousemove drop paths.

Three affordances now read these canonical edges, so they align **by construction** rather than by coincidence:
- **Grab handle** — [src/text-objects/TextObjectGrabHandle.tsx](../../src/text-objects/TextObjectGrabHandle.tsx) resolves one frame per block. Which of TWO readings applies is decided ONCE in `block-frame.ts` (`BlockFrame.columnRight`, task 487/483): a block WITH a marker of its own **hugs** it (`markerLeft − gapPx − HANDLE_WIDTH`); a markerless CONTAINER has nothing to hug, so it **OCCUPIES the marker column of the level ABOVE** — the column its structure hangs from, empty on this row — right-justified to that column's inner edge. Non-overlap is then a PROPERTY (two levels sit in two different columns) rather than a separation target, and the gutter reads outward-in as a breadcrumb: each handle under its own level's bullet. A container with no column above it (a top-level list) takes the ordinary markerless slot, its own content edge. The slimmed [handle-layout.ts](../../src/text-objects/handle-layout.ts) is now just that arithmetic (`computeHandleLeft`) over the frame's `markerLeft` / `gapPx`. Task 527 swept the four sites where 487's PREDECESSOR was still stated as live — above all `globals.css`'s `:root` block, the SSOT a designer opens before touching `--margin-track-width`, which described the retired container STEP and drew the ~20px blob task 483 measured. The token's real and only role is the #49 left-of-content fallback for the two example marker kinds; `BlockFrame.depth` and the `trackWidthPx` parameters that fed it are DELETED (zero readers, and `countUuidAncestors` was walking the chain per hover placement for a value nobody read). Since task 382 the handle resolves a **LANE**, `[floor … cap]`, not a point: `markerLeft` is the MEASURED marker string where the build can measure it (`text-metrics.ts`, never a hard-coded glyph width) — task 487 retired the band-MIDDLE stand-in, which drifts steadily left of the bullet as the band deepens, detaching an item's handle from the very thing it labels; the middle survives only as the fallback where no canvas is available, and two later passes — the narrow-viewport floor and task 353's same-row separation, which had no upper bound at all — used to push the box onto the bullet glyph. The cap derives from `inkLeft`, the leftmost document INK on that row, resolved BESIDE the anchor by `resolveMarkerGeometry` so the two can never disagree; the FLOOR outranks the CAP (an unreachable handle is worse than an overlapping one), and the bound is per-ROW from the widest marker the list can render. The `.tiptap ul/ol` marker band went 1.5em → 2em (task 382, so the cap stays a rare-case net) and then 2em → **2.5em** (task 487), which is the column rule's price stated as an inequality rather than a taste: the band must hold one row's geometry whole — `band > markerInk + 0.25em trail + --margin-handle-gap + 12px`, and at 2em a `•` does not fit at all (the deficit IS the 4.25px handle overlap 483 measured on a top-level list). Task 353's inboard separation gained a SECOND, outboard pass: where the inboard push has run out of lane, the OUTER handle gives way into the margin instead, bounded by the floor — free by construction, since nothing on a row lies left of that row's own marker. Which handles show is a separate rule, settled by task 425: the hovered item ALWAYS gets one, and a container gets one ONLY when the hovered line is that container's own top row (`isTopRowOf`, walking the same `GRABBABLE_CHILD_SELECTOR` descent the placement performs, so "is this the top row" and "where does the container's handle go" cannot disagree). The set is restricted innermost-first BEFORE placement, so `computePlacement` runs at most twice per hover; under the list schema that caps the visible set at 2 by construction rather than by a cap.
- **Hover zone ≡ handle lane** — task 526: the strip that REVEALS a handle IS the lane it may OCCUPY. The handle's extent is EM-SCALED per block (a `0.625em` gap off the block's own font, plus the chip-3 hit/hover halo at `1.8 × --editor-font-size`, centred on the 12px box) while the zone that kept it alive was a fixed px constant off a different concept entirely — so a `\section` heading's target stuck 7.2px past the zone and a `\part`'s 10.7px, and the handle VANISHED as the user reached for it (measured; the prose row cleared by 0.8px, i.e. at exactly one point in a 12-step preference range). `hoverZoneLeft` is now `handleLaneFloor`, the same expression `resolveHandleLane` floors on. Widening the zone CREATES a second occupant, so the lane resolves outboard → inboard: the fold-chevron COLUMN places first (`BlockFrame.chevronRight`, reserved per ROW and gated on the block's KIND — never a DOM probe, which on a source pod would walk a whole CodeMirror subtree per hover) and the handle takes what remains, box AND halo, through the ONE `--margin-handle-hit-cap` the sibling clamp already writes. A prose row keeps its FULL halo. `--margin-col-chevron-width` is a token now, since the reservation needs it.
- **Handle hierarchy** — task 394 retired 353's `descendTo` hint: **every handle anchors at its OWN block's first visual line**, so a nested list shows one handle per containing level at four distinct rows (an outward-in structural breadcrumb) instead of stacking all of them on the hovered row, where the innermost was pushed onto the bullet. Visibility stays hover-scoped to the containing chain (353 points 1–2 unchanged) and the same-row separation + ink cap survive for GENUINE coincidences (a list's first row really is one line shared by two levels). The fix is a DELETION — one rule, no special case — and a container's first grabbable child IS its own first visual line, since a `<ul>` has no text line of its own. Decided default: a container whose first line has scrolled off-screen paints its handle off-screen with it.
- **Drop indicator** — [src/components/drop-mode/hit-test.ts](../../src/components/drop-mode/hit-test.ts) takes the between-blocks + expex drop bars' x/width from `resolveContentEdges`, the same content extent the grab handles get.

## Hint system (tooltips + Helper mode)

Virgil has **one** app-wide hover/focus-hint primitive: [src/components/HintLayer.tsx](../../src/components/HintLayer.tsx) — the single delegated controller + portal bubble, mounted once near the root in [src/app/page.tsx](../../src/app/page.tsx). It is the production replacement for native `title=""` tooltips and the engine behind Helper mode. One set of capture-phase `document` listeners resolves the hinted element under the pointer/focus via `closest('[data-hint],[data-hint-keys],[data-helper]')` (O(ancestor-depth), never doc-size, not an `editor.on` subscriber), positions a single `.hint-bubble` portal via `useFloatingMenuPosition`, and dismisses on Escape / scroll / pointer-down / pointer-leave / focus-out.

Authoring is via [src/components/Hint.tsx](../../src/components/Hint.tsx): `useHint({ label, keys, pos })` returns spreadable `data-hint*` attributes, or `<Hint label keys pos>` wraps a child element. The attribute protocol: `data-hint` (text, optional), `data-hint-keys` (a portable shortcut string), `data-hint-pos` (`above|below|left|right` nudge; defaults below, flipping to a `[data-strip-side]` ancestor's side). A **shortcut-only** hint omits the label so the bubble shows just the keycap. Legacy `data-helper` / `data-helper-pos` are read as aliases for incremental migration off `title=`; the old CSS `::after` callout is gone (the bubble is JS).

For an **icon-only** control the visible label *is* its accessible name, so both come from ONE string via `iconHint({ label, hint?, keys?, pos? })` (task 281) — it returns `aria-label` alongside the `data-hint*` attributes, so a tooltip and an accessible name can't drift apart or be half-forgotten. `hint` overrides the bubble text where the tooltip should say more than the name. It's a plain function rather than a hook, deliberately: per-row close buttons are built inside a `.map`, where a hook can't go. Separately, `.focus-ring` unbundles the focus **indicator** from a control's geometry, so an icon button's ring no longer inherits whatever box its layout happened to give it.

[src/components/Kbd.tsx](../../src/components/Kbd.tsx) renders a portable shortcut string (`"Mod+/"`, `"Mod+Shift+N"`, …) as a platform-aware keycap chip in system sans — `Mod` → ⌘ on Mac, `Ctrl` elsewhere — via `isMac()` in [src/lib/platform.ts](../../src/lib/platform.ts) (the single Mac probe; SSR-safe `useIsMac()` external-store read). It's the only way to render a shortcut — no hardcoded `⌘…` strings.

**Cmd+/ (`Mod+/`)** toggles the actions menu: a window-level keydown handler in [SelectionActionsMenu.tsx](../../src/components/SelectionActionsMenu.tsx) (~line 452) opens the `ActionsMenuPanel` at the live cursor/selection (the keyboard twin of clicking the margin ⚡), and toggles it closed if already open. The margin `SelectionActionsMenu` button carries a shortcut-only `useHint({ keys: "Mod+/" })` hint (the ⚡ glyph + ⌘/ keycap).

**Helper mode** is just the instant, always-on rendering of the same hints: toggled from the "?" button on the Virgil bar (circle-question-mark icon, next to the info "i" button); when active `document.body` gets `data-helper-mode="on"`, `HintLayer` drops the hover delay to 0, and a "Helper mode" indicator appears in the Virgil bar (styled like the Focus View indicator — click to deactivate). State: `useHelperMode()` in [src/hooks/useHelperMode.ts](../../src/hooks/useHelperMode.ts) — module-scoped `useSyncExternalStore` (same shape as `useZenMode`), exports `{ on, toggle, set }`, persists to localStorage key `virgil-helper-mode`.

See [src/STYLE_GUIDE.md](../../src/STYLE_GUIDE.md) → "Hints, tooltips & keyboard shortcuts" for authoring guidelines (label length, positioning zones, accessibility).

**CoworkPenBadge** ([src/components/CoworkPenBadge.tsx](../../src/components/CoworkPenBadge.tsx)) is the topbar pill that says WHY the editor has gone read-only while an `/editor/*` skill is committing (task 489). ## Dialogs, scrim & z-tiers

**A control PAIR is spelled once, like a control family** (task 501). `CommitActions` ([src/components/CommitActions.tsx](../../src/components/CommitActions.tsx)) is the Keep / Dismiss pair for a pending AI change — the two buttons, their announced strings, their sizing and their glyph — shared by the `PendingChangePill` margin portal and `suggestion-fields`' applied-card body, which had carried byte-identical copies under two glyph names. The CONTAINER is deliberately not shared (a fixed portal and a card row are different chrome). It also landed the **affirmative role family**: the positive half now reads `--positive` / `text-positive-ink` / `hover:bg-positive-soft`, mirroring the destructive half's `--danger` tokens, where it had been a raw `text-emerald-600` four lines from a token-reading sibling. STYLE_GUIDE → *Buttons* / *The affirmative family*.

Modal dialogs (`SystemDialog` / `ConfirmDialog` / imperative `confirm`/`prompt`) were de-browned in 1c243822: the `primary` Button variant now backs onto `--btn-primary` (→ taupe `--control-selected`), so affirmative buttons render taupe, not the saturated `--accent` brown (`--accent` stays on links/marks/CTAs). The modal **scrim** `--overlay-scrim` is re-derived from `--ink-strong` (warm near-black), and the dialog surface adopts the `--shadow-float` token.

Form controls inside dialogs go through the field primitives — `Input` / `Textarea` / `Select`, all three built on one `fieldChrome()` ([src/components/field-primitives.tsx](../../src/components/field-primitives.tsx), task 190) — the text-field twin of what `Button` always was for buttons. Don't hand-roll a bordered input; take the primitive and pick a `tone` / `ink` / `density`. See STYLE_GUIDE "Text fields".

The modal/tooltip **z-tiers are named** in [src/floats/float-policy.ts](../../src/floats/float-policy.ts): `DROP_INDICATOR_Z` (9999), `MODAL_SCRIM_Z` (10000), `HINT_Z` (10010), plus `OPEN_CHROME_MENU_Z` — the tier shared by the `<Menu>` primitive, `NodeEditPopover`, and (since 29cad190) the caret popups (`SlashCommandPopup`, promoted off the ad-hoc `zIndex:1000` so a popped card / lifted overlay can no longer occlude them). The full ladder is documented in `STYLE_GUIDE.md`.

**Enter activates the CUED default** (task 389). The accented footer button is a *visible promise*, so `Enter` must keep it: [dialog-enter-policy.ts](../../src/components/dialog-enter-policy.ts) resolves the key against the focused in-frame button, else the REGISTERED cue — never gated on where DOM focus happens to sit. (Pre-389 it was: the cue was claimed by a one-shot `requestAnimationFrame` scheduled from a commit that renders `null` — `mounted` starts false — so on a busy main thread the frame beat the re-render, the claim missed, and `Return` did nothing. The reported case was the re-anchor confirm at the end of a drag.) The exceptions are asked of the **TARGET**, not of focus: a control that owns `Enter` keeps it (textarea, contenteditable, `select`, link, `<summary>`), and so does anything that consumed the key with `preventDefault()`. `Shift+Enter` and a held (`repeat`) Enter are not the cue's key. Dialogs genuinely stack, so [dialog-stack.ts](../../src/components/dialog-stack.ts) is a LIFO where only the **owner** answers a key — the topmost MODAL outranks everything, and between two non-modals (Preferences, the bug reporter) the window CONTAINING focus wins — which also retired a live bug where a single `Escape` closed both stacked dialogs. `SystemDialog` owns initial focus through an `initialFocus` door and stands down when the dialog's own body claims it (task 389b: the stand-down branch was DEAD in all three dialogs written for it, because a caller's `useEffect` fires in the commit where the body is not yet in the DOM). `confirmDialogCuedDefault()` derives `autoFocus` for every caller, so a `tone="danger"` action is never the cued default. CI: `dialog-cued-default-census.test.ts` — membership DISCOVERED from the tree, and a footer that deliberately cues nothing must DECLARE `noCuedDefault` rather than merely omit one.

**The `tone` → BUTTONS mapping is stated once, for BOTH doors** (task 528). Virgil has two imperative confirms — `useConfirmDialog()` and `useSystemDialog()` — and they are separate implementations, so the second hand-derived both answers and a `tone: "danger"` confirm there opened with the DESTRUCTIVE button cued: `Enter`, the key the user has been trained is safe, ran the destruction. `confirmDialogCuedDefault()` and `confirmActionVariant()` now live in the import-free leaf [confirm-cue-policy.ts](../../src/components/confirm-cue-policy.ts) that both doors read. Its second rule: **a button that COMMITS NOTHING is never painted destructive** — a `danger` ALERT's sole button merely dismisses, so it takes the neutral variant and the tone goes to the MESSAGE ink (STYLE_GUIDE → "the destructive / alarm family": red is a claim about the AFFORDANCE, not about severity). CI: `dialog-enter-contract.test.tsx` drives the REAL host end to end and asserts the PROMISE resolves `false`; a second census walks every dialog button.

**A dialog that can hold a DRAFT declares what a dismissal costs** (task 530). `SystemDialog` has always owned every dismiss TRIGGER (Escape via the stack, the modal backdrop, the scrimless outside-mousedown) and nobody owned what a dismissal COSTS — so `StyleEditorModal`, the one dialog whose draft is the only copy of real typed work, discarded a hand-authored preamble on one stray backdrop click with no warning. Every dialog now declares `dismissGuard` (asked by the ONE `requestDismiss` door before it closes; may return a promise, so a guard can raise its own confirm) or `dismissIsFree`, and the footer Cancel asks too — otherwise the one dismissal the user performs DELIBERATELY is the one that discards silently. Three legitimate free shapes, each stated at the site: a draft that OUTLIVES the close (an always-mounted window with an `open` prop), a dismissal that IS the abandonment (the `prompt` arm), and fields that commit UPSTREAM. The other half is that an INNER step aborting is something the shell cannot see, so it travels as a REPORT the caller returns (`NewDocumentModal`'s `NewDocumentOutcome`) rather than a close the caller performs — cancelling the folder picker no longer throws away the typed name. CI: `dialog-dismiss-census.test.ts`, allowlists EMPTY.

**Focus goes back where it came from** (task 531). Every `SystemDialog` took DOM focus on open and none gave it back, so closing a confirm by any route left the caret stranded on `<body>` and the user's next keystroke went nowhere. The shell took the focus, so the shell gives it back: one effect keyed on `open` captures `document.activeElement` at the open edge and restores it (with `preventScroll`) in its cleanup. It FAILS SAFE (an element that has since unmounted restores nothing) and STANDS DOWN (something that already claimed focus keeps it). One call site had hand-rolled the missing restore and said so in a comment; that copy is retired. CI: `dialog-focus-restore.test.tsx`.

**A declared VARIANT is a promise that some caller asks for it** (task 515). `SystemDialog`'s positioning taxonomy is a `STYLE_GUIDE` table telling the next author which member to reach for, and the `anchored` variant — plus the `at={{x,y}}` and `outsideClickGuard` props that served it — had lost its last production caller when task 495 retired `PreferenceModePicker`, leaving three pieces of a shell every dialog mounts pinned only by their own suite. All three are DELETED (`<Menu>` + `useFloatingMenuPosition` already own the two anchored shapes STYLE_GUIDE routes elsewhere). CI: `system-dialog-variants-census.test.ts` — members DISCOVERED from the union's own declaration, the DEFAULT member called by OMISSION, an unresolvable `variant={expr}` failing CLOSED, allowlist EMPTY.

**A field whose value lives elsewhere holds a DRAFT and RECONCILES** (tasks 529 / 532). Two rules, both about an inline field that edits a value some OTHER thing owns (a preference store, a sidecar record, a node attr):
- **An edit session ends exactly ONCE** ([src/lib/field-edit-session.ts](../../src/lib/field-edit-session.ts)). `element.blur()` dispatches `focusout` SYNCHRONOUSLY and React delegates `onBlur` off it, so a `.blur()` inside a keydown handler runs that field's own commit *nested inside the still-executing keydown*, from the render closure it captured. Four fields ended twice: Escape ran the commit with the value it was cancelling (the figure width box resized the figure, the citation `+range` wrote the abandoned range into the `\cite` AND the sidecar, the reader's page box scrolled to the page it promised to abandon) and Enter ran it twice. `useFieldEditSession` holds the record synchronously, in a ref, for exactly the blur's dispatch; `commitLiveValue` is its liveness half — a deferred commit that cannot read a live value REFUSES rather than writing `""` over a title the user never touched.
- **A field holds a DRAFT, commits on a stated edge, and reconciles while not dirty** ([src/components/field-draft.ts](../../src/components/field-draft.ts)). The user's intermediate keystrokes are not the value: a hex box passes through `#`, `#c4` and a backspace on the way to `#c45a5a`, none of which is a color. `SmartPreferences`' panel-typography grid had a `value={typo.color}` with an `onChange` that wrote only a COMPLETE `#rrggbb`, which under React's controlled-input contract means the box could not be typed into or backspaced at all. `HexColorField` ([src/components/HexColorField.tsx](../../src/components/HexColorField.tsx)) is now Virgil's ONE editable color field — swatch + hex text, auto-`#`, validate-on-commit with an `invalid` flash, Enter → blur — and both sites render it.

**"Don't show this again" is a capability of the DOOR** (task 492). A confirm guarding a deliberate, REVERSIBLE gesture is pure friction once read, so `confirm()` takes one `suppressId` field ([src/components/confirm-suppression.ts](../../src/components/confirm-suppression.ts)) and owns the checkbox, the persisted answer and the short-circuit. Two confirms opt in: `archive-atom-marker` (archiving a footnote removes its marker) and `reanchor-margin-item` (raised at the end of a full drag — the most deliberate gesture in the app). The rule with teeth is that a **`tone: "danger"` confirm may NEVER be suppressible** — remembering "yes" for a destruction is the trap task 386 removed from the keyboard, arriving through persistence instead — and the refusal is stated once, in the door. The answer is GLOBAL, which repaired the retired `suppressArchiveAtomWarning` pref's per-window scope (the tick had to be re-made in every window); `loadPrefs` folds the old key across once.

**NodeEditPopover** ([src/components/NodeEditPopover.tsx](../../src/components/NodeEditPopover.tsx)) is the **unified** math + figure edit popover (29cad190 merged the deleted `MathPopover.tsx` + `FigurePopover.tsx` onto one shared skeleton — commit-once guard, click-outside-commits, Escape, auto-focus — with a per-family view branch: math Escape COMMITS + KaTeX preview + Cancel; figure Escape CANCELS + Mod+Enter).
